Arquitectura Propuesta para FarmaNorte

La arquitectura propuesta para FarmaNorte tiene como objetivo unificar la información de ventas, stock y logística para incorporar un modelo de previsión de demanda, reducir las roturas de stock y el capital inmovilizado en almacén. A continuación, se describe la arquitectura propuesta:

Introducción

La empresa FarmaNorte, dedicada a la distribución farmacéutica, cuenta con aproximadamente 350 empleados y busca mejorar su gestión de datos y procesos. La arquitectura propuesta se basa en un enfoque Lakehouse con capas medallion, que permite una integración eficiente y escalable de los datos. El objetivo es proporcionar una solución escalable y eficiente en la nube, preferentemente en Azure.

Componentes de la Arquitectura

  • Cloud Provider: Azure, como proveedor de nube preferido por el cliente, ofrece una amplia gama de servicios y herramientas para desarrollar y desplegar la solución.
  • Plataforma de Datos: Azure Synapse Analytics (antes Azure SQL Data Warehouse) será la plataforma de datos unificada para almacenar y analizar los datos de ventas, stock y logística. Su escalabilidad y eficiencia en el análisis de datos la hacen ideal para este proyecto.
  • Herramienta de Visualización: Power BI será la herramienta de visualización para crear informes y dashboards interactivos. Su facilidad de uso y capacidad para conectarse a Azure Synapse Analytics la hacen una opción adecuada.
  • Modelo de Machine Learning: Azure Machine Learning se utilizará para desarrollar y desplegar el modelo de previsión de demanda. Su capacidad para desarrollar y desplegar modelos de machine learning escalables y eficientes la hace ideal para este proyecto.
  • Integración de Datos: Azure Data Factory se encargará de integrar los datos de los diferentes orígenes (ERP, sistema de almacén y CRM de ventas) y almacenarlos en Azure Blob Storage. Su facilidad de uso y escalabilidad en la integración de datos la hacen una opción adecuada.

Capas de la Arquitectura

La arquitectura se compone de las siguientes capas:

  • Capa de Ingesta: Azure Data Factory se encargará de ingerir los datos de los diferentes orígenes (ERP, sistema de almacén y CRM de ventas) y almacenarlos en Azure Blob Storage.
  • Capa de Procesamiento: Azure Synapse Analytics procesará los datos ingeridos y los transformará en un formato adecuado para el análisis y el modelado.
  • Capa de Análisis: Power BI se conectará a Azure Synapse Analytics para crear informes y dashboards interactivos.
  • Capa de Machine Learning: Azure Machine Learning se utilizará para desarrollar y desplegar el modelo de previsión de demanda, que se integrará con Azure Synapse Analytics.

Justificación de la Arquitectura

La arquitectura propuesta se justifica por la siguiente:

  • Escalabilidad: Azure Synapse Analytics y Azure Blob Storage ofrecen escalabilidad y eficiencia en el almacenamiento y análisis de datos.
  • Eficiencia: La integración de datos mediante Azure Data Factory y la visualización mediante Power BI ofrecen eficiencia en la gestión de datos.
  • Facilidad de uso: Power BI y Azure Machine Learning ofrecen facilidad de uso para la creación de informes y modelos de machine learning.

Suposiciones y Restricciones

  • Se asume que el cliente tiene una cuenta en Azure y que se puede utilizar la infraestructura existente.
  • Se considera que el plazo objetivo de 3-4 meses es factible con la arquitectura propuesta.
  • Se tiene en cuenta la restricción presupuestaria de 150.000 a 200.000 euros para la selección de servicios y plataformas.

Conclusión

La arquitectura propuesta para FarmaNorte permite una integración eficiente y escalable de los datos, así como la creación de un modelo de previsión de demanda utilizando machine learning. La selección de servicios y plataformas en Azure se justifica por la escalabilidad, eficiencia y facilidad de uso que ofrecen. Se considera que la arquitectura propuesta cumple con los objetivos y requisitos del proyecto, y se espera que permita al cliente alcanzar los KPIs de éxito definidos.

Análisis Crítico del Problema de Negocio y Madurez de Datos Actual

FarmaNorte, una empresa de distribución farmacéutica con aproximadamente 350 empleados, enfrenta desafíos en la gestión de sus datos y procesos. Actualmente, la empresa utiliza Excel para consolidar informes de ventas de forma manual semanal, sin contar con un data warehouse ni una plataforma de Business Intelligence (BI) en producción. Esto indica una madurez analítica limitada y una dependencia de procesos manuales, lo que puede llevar a ineficiencias y errores.

La empresa busca unificar su información de ventas, stock y logística para incorporar un modelo de previsión de demanda. Esto tiene como objetivo reducir las roturas de stock y el capital inmovilizado en almacén. La falta de integración de datos y la ausencia de análisis avanzados limitan la capacidad de la empresa para tomar decisiones informadas y optimizar sus operaciones.

Propuesta de Funcionalidades Clave de IA/Data

Para abordar los desafíos de FarmaNorte, se proponen las siguientes funcionalidades clave de IA/Data:

  1. Modelo de Previsión de Demanda: Desarrollar un modelo de machine learning que prediga la demanda futura de productos farmacéuticos basándose en datos históricos de ventas, estacionales y tendencias del mercado. Esto permitirá a la empresa optimizar su inventario y reducir las roturas de stock.
  2. Análisis de Roturas de Stock y Optimización de Inventario: Implementar un análisis que identifique patrones y causas de roturas de stock. Esto permitirá a la empresa tomar medidas proactivas para evitarlas y optimizar su inventario.
  3. Integración de Datos y Visualización: Integrar datos de ventas, stock y logística en una plataforma de datos unificada y proporcionar visualizaciones interactivas para que los usuarios puedan explorar y analizar los datos de manera efectiva.

Roadmap Técnico

A continuación, se detalla el roadmap técnico para cada funcionalidad:

  1. Modelo de Previsión de Demanda:
  • Fuentes de datos: Datos históricos de ventas, información de productos, estacionales y tendencias del mercado.
  • Tipo de análisis: Machine learning (regresión, series temporales).
  • Integración en el flujo de trabajo: El modelo se integrará con la plataforma de datos unificada y se utilizará para generar previsiones de demanda que se visualizarán en dashboards interactivos.
  1. Análisis de Roturas de Stock y Optimización de Inventario:
  • Fuentes de datos: Datos de stock, pedidos y entregas.
  • Tipo de análisis: Análisis de datos exploratorio, identificación de patrones y causas.
  • Integración en el flujo de trabajo: El análisis se integrará con la plataforma de datos unificada y se utilizará para identificar oportunidades de mejora en la gestión de inventario.
  1. Integración de Datos y Visualización:
  • Fuentes de datos: Datos de ventas, stock y logística.
  • Tipo de análisis: Integración de datos, visualización de datos.
  • Integración en el flujo de trabajo: La plataforma de datos unificada se utilizará para integrar los datos y proporcionar visualizaciones interactivas para los usuarios.

Valor de Negocio

La implementación de estas funcionalidades tendrá un impacto significativo en las métricas de éxito de FarmaNorte:

  • Reducción de Roturas de Stock: El modelo de previsión de demanda y el análisis de roturas de stock permitirán a la empresa reducir las roturas de stock en al menos un 30%.
  • Disminución del Inventario Inmovilizado: La optimización de inventario permitirá a la empresa liberar capital inmovilizado en almacén, mejorando su eficiencia financiera.
  • Exactitud del Modelo de Previsión de Demanda: La implementación de un modelo de previsión de demanda preciso permitirá a la empresa tomar decisiones informadas y optimizar sus operaciones, con una exactitud por encima del 85%.

En resumen, la propuesta de funcionalidades clave de IA/Data para FarmaNorte tiene como objetivo abordar los desafíos de la empresa en la gestión de datos y procesos. La implementación de estas funcionalidades tendrá un impacto significativo en las métricas de éxito de la empresa, mejorando su eficiencia operativa y financiera.

Power BI ofrece una amplia gama de características y herramientas para visualizar los datos, incluyendo gráficos, tablas y mapas.

Conclusión

La estrategia de visualización de datos para FarmaNorte tiene como objetivo proporcionar una visión clara y concisa de los datos de ventas, stock y logística, permitiendo a los usuarios tomar decisiones informadas y optimizar las operaciones de la empresa. La implementación de la plataforma de visualización de datos y la definición de KPIs permitirán a la empresa medir el éxito de la estrategia y tomar decisiones informadas para mejorar su eficiencia operativa y financiera.

Análisis de Fuentes de Datos para FarmaNorte

1. Inventario de Fuentes Identificadas

Basándome en la propuesta de solución presentada, he identificado las siguientes fuentes de datos relevantes para el proyecto:

  1. Sistema de Gestión de Ventas:
  • Tipo de datos: Ventas, cantidad vendida, fechas de venta, precios.
  • Relevancia: Fundamental para el modelo de previsión de demanda y análisis de roturas de stock.
  • Formato: Estructurado (probablemente en formato de base de datos relacional).
  • Frecuencia de actualización: Diaria (o en tiempo real, dependiendo de la configuración del sistema).
  • Riesgos/Dependencias: Calidad de los datos de ventas, integridad de los registros.
  1. Sistema de Gestión de Inventarios:
  • Tipo de datos: Niveles de stock, ubicaciones de almacenamiento, movimientos de inventario.
  • Relevancia: Crucial para el análisis de roturas de stock y gestión de inventarios.
  • Formato: Estructurado (posiblemente en un sistema de gestión de inventarios específico).
  • Frecuencia de actualización: En tiempo real o diaria, según la implementación.
  • Riesgos/Dependencias: Precisión de los datos de inventario, actualizaciones oportunas.
  1. Sistema de Logística y Distribución:
  • Tipo de datos: Pedidos, entregas, tiempos de entrega, costos de transporte.
  • Relevancia: Importante para la comprensión de la cadena de suministro y su impacto en las ventas y el stock.
  • Formato: Estructurado o semiestructurado (en formato CSV, JSON, o similar).
  • Frecuencia de actualización: Variable, dependiendo de la frecuencia de los pedidos y entregas.
  • Riesgos/Dependencias: Calidad de los datos de logística, integración con sistemas de terceros.
  1. Datos de Mercado y Competencia:
  • Tipo de datos: Tendencias de mercado, comportamiento de la competencia, análisis de la oferta y la demanda.
  • Relevancia: Útil para ajustar el modelo de previsión de demanda y estrategias de marketing.
  • Formato: No estructurado o semiestructurado (informes de investigación, noticias, redes sociales).
  • Frecuencia de actualización: Ad-hoc o periódica, dependiendo de la disponibilidad de datos.
  • Riesgos/Dependencias: Calidad y relevancia de los datos, posibles sesgos en la interpretación.
  1. Dados de Clientes y Preferencias:
  • Tipo de datos: Perfiles de clientes, historial de compras, preferencias.
  • Relevancia: Valioso para personalizar la experiencia del cliente y ajustar estrategias de marketing.
  • Formato: Estructurado (bases de datos de clientes) y no estructurado (comentarios, redes sociales).
  • Frecuencia de actualización: Continua, a medida que los clientes interactúan con la empresa.
  • Riesgos/Dependencias: Privacidad y seguridad de los datos de clientes, consentimiento para el uso de datos.

2. Evaluación de Calidad y Riesgos por Fuente

  • Sistema de Gestión de Ventas: Alto riesgo de datos inconsistentes o no actualizados.
  • Sistema de Gestión de Inventarios: Riesgo moderado de desactualización o error en los registros.
  • Sistema de Logística y Distribución: Riesgo bajo a moderado, dependiendo de la integración con terceros.
  • Datos de Mercado y Competencia: Alto riesgo de sesgo y dificultad en la calidad y relevancia de los datos.
  • Datos de Clientes y Preferencias: Alto riesgo relacionado con la privacidad y seguridad de los datos.

3. Dependencias y Supuestos Asumidos

  • Se asume que los sistemas de gestión de ventas, inventarios y logística están bien implementados y ofrecen datos confiables.
  • Se supone que hay acuerdos en lugar para el uso de datos de terceros (como datos de mercado y competencia).
  • Se depende de la cooperación de los departamentos de ventas, logística y marketing para la recopilación y calidad de los datos.
  • Se asume que la empresa tiene las herramientas y recursos necesarios para manejar y analizar grandes cantidades de datos.

4. Recomendaciones Prioritarias para la Fase de Ingesta

  1. Validación de Calidad de Datos: Antes de la ingesta, validar la calidad y consistencia de los datos en cada fuente para asegurar su precisión y utilidad.
  2. Establecimiento de Acuerdos con Terceros: Para datos de mercado y competencia, asegurar que se tienen los acuerdos necesarios para el uso de estos datos.
  3. Implementación de Medidas de Seguridad: Para proteger la privacidad y seguridad de los datos de clientes, implementar medidas de seguridad robustas.
  4. Desarrollo de un Plan de Integración: Desarrollar un plan detallado para la integración de los diferentes sistemas y fuentes de datos, considerando las frecuencias de actualización y los formatos de los datos.
  5. Capacitación del Personal: Capacitar al personal involucrado en el manejo y análisis de datos sobre las mejores prácticas de manipulación y seguridad de datos.

Este análisis sentará las bases para la fase de ingesta, asegurando que se consideren los riesgos y dependencias clave y se tomen las medidas necesarias para garantizar la calidad y utilidad de los datos para el proyecto de FarmaNorte.

02 Ingesta de Datos

Estrategia y pipelines con Azure Data Factory
Azure Data Factory

Estrategia de Ingesta de Datos para FarmaNorte con Azure Data Factory

1. Patrón de Ingesta por Fuente o Grupo de Fuentes

Basándome en el análisis de fuentes de datos realizado, se recomienda el siguiente patrón de ingesta para cada fuente o grupo de fuentes:

  • Sistema de Gestión de Ventas: Ingesta por lotes (batch) diaria, debido a la naturaleza de los datos y la frecuencia de aktualización.
  • Sistema de Gestión de Inventarios: Ingesta en tiempo real o cerca de tiempo real ( Near Real-Time, NRT) para reflejar los cambios en el inventario de manera oportuna.
  • Sistema de Logística y Distribución: Ingesta por lotes (batch) con una frecuencia ajustada según la frecuencia de los pedidos y entregas, que podría ser diaria o semanal dependiendo de la actividad.
  • Datos de Mercado y Competencia: Ingesta ad-hoc o periódica, dependiendo de la disponibilidad de los datos y su relevancia para el modelo de previsión de demanda.
  • Datos de Clientes y Preferencias: Ingesta en tiempo real o cerca de tiempo real para capturar las interacciones de los clientes y actualizar sus perfiles y preferencias de manera continua.

2. Estructura de Pipelines Recomendada en ADF

Se sugiere una estructura de pipelines modulares en Azure Data Factory (ADF), donde cada pipeline se centre en una fuente de datos específica o en un conjunto de fuentes relacionadas. Esto facilitará el manejo, la depuración y el mantenimiento de los pipelines. La estructura recomendada incluye:

  • Un pipeline por cada fuente de datos principal (ventas, inventarios, logística, etc.).
  • Pipelines adicionales para la integración de datos de mercado y competencia, y para la ingesta de datos de clientes y preferencias.
  • Un pipeline de "orquestación" que coordine la ejecución de los pipelines individuales y maneje las dependencias entre ellos.

3. Conectores y Configuraciones Clave

Para cada fuente de datos, se deben utilizar los conectores de ADF más adecuados. Algunos de los conectores y consideraciones clave incluyen:

  • Sistema de Gestión de Ventas: Utilizar el conector de base de datos relevante (por ejemplo, SQL Server, Oracle) para conectar con el sistema de gestión de ventas.
  • Sistema de Gestión de Inventarios: Similar al sistema de ventas, utilizar el conector adecuado para el sistema de gestión de inventarios.
  • Sistema de Logística y Distribución: Dependiendo del formato de los datos (CSV, JSON, etc.), utilizar conectores como Azure Blob Storage o Azure Data Lake Storage para la ingesta de datos.
  • Datos de Mercado y Competencia: Utilizar conectores a fuentes de datos externas como APIs de terceros o servicios de datos en la nube.
  • Datos de Clientes y Preferencias: Utilizar conectores a sistemas de gestión de relaciones con el cliente (CRM) o a bases de datos que almacenan perfiles de clientes y sus interacciones.

4. Cadencias y Dependencias entre Pipelines

La cadencia de ejecución de cada pipeline dependerá de la frecuencia de actualización de los datos y de las necesidades del negocio. Por ejemplo:

  • Los pipelines para sistemas de gestión de ventas e inventarios podrían ejecutarse diariamente durante la noche para reflejar las transacciones del día.
  • El pipeline para el sistema de logística y distribución podría ejecutarse semanalmente, dependiendo de la frecuencia de los pedidos y entregas.
  • Los pipelines para datos de mercado y competencia, y para datos de clientes y preferencias, podrían ejecutarse según sea necesario o en una base regular (mensual, trimestral) dependiendo de la disponibilidad de los datos y su impacto en el modelo de previsión de demanda.

Las dependencias entre pipelines deben gestionarse cuidadosamente. Por ejemplo, el pipeline de orquestación podría asegurarse de que los pipelines de ingesta de datos se completen antes de proceder con cualquier proceso de transformación o análisis.

5. Riesgos Identificados y Recomendaciones de Mitigación

Se han identificado varios riesgos en las fuentes de datos, incluyendo la calidad de los datos, la seguridad y la privacidad, especialmente para los datos de clientes y preferencias. Para mitigar estos riesgos:

  • Validación de Calidad de Datos: Implementar un proceso de validación y limpieza de datos antes de la ingesta para asegurar la calidad y consistencia de los datos.
  • Medidas de Seguridad: Implementar medidas robustas de seguridad y privacidad para proteger los datos de clientes y preferencias, como cifrado, acceso controlado y cumplimiento de regulaciones como el GDPR.
  • Acuerdos con Terceros: Asegurarse de tener acuerdos claros y actualizados con terceros para el uso de sus datos, especialmente para datos de mercado y competencia.
  • Capacitación del Personal: Capacitar al personal sobre las mejores prácticas de manejo y seguridad de datos para minimizar el riesgo de errores humanos.

Al adoptar esta estrategia de ingesta de datos, FarmaNorte podrá asegurar una ingesta eficiente, segura y de alta calidad de sus fuentes de datos, lo que será fundamental para el éxito de su proyecto de lakehouse y modelo de previsión de demanda.

03 Almacenamiento

Arquitectura de Data Lake con capas medallion
ADLS Gen2 · Synapse

Propuesta de Arquitectura de Almacenamiento para FarmaNorte

1. Decisión y Justificación sobre la Estructura de Capas

Basándome en el análisis de las fuentes de datos y la estrategia de ingesta definida, recomiendo una arquitectura de almacenamiento que utilice una estructura de capas medallion simplificada, específicamente Bronze y Silver, en lugar de la arquitectura completa Bronze/Silver/Gold. Esta decisión se justifica por el volumen moderado de datos y la madurez del equipo del cliente.

La capa Bronze se utilizará para almacenar los datos raw, tal como se ingieren de las fuentes, sin transformaciones significativas. La capa Silver será utilizada para almacenar los datos transformados y preparados para el análisis. Esta estructura permitirá una buena calidad de datos y una mayor eficiencia en el procesamiento, sin la necesidad de una capa Gold que implica una mayor complejidad y madurez en el uso de los datos.

2. Servicios de Azure Recomendados y Justificación

  • Azure Data Lake Storage Gen2 (ADLS Gen2): Será utilizado como almacenamiento principal para los datos, tanto en la capa Bronze como en la Silver. ADLS Gen2 ofrece una gran escalabilidad, seguridad y compatibilidad con diversos servicios de Azure.
  • Azure Data Factory (ADF): Se utilizará para la ingesta de datos y para orquestar las transformaciones entre las capas Bronze y Silver. ADF es ideal para la integración de datos y ofrece una amplia gama de conectores.
  • Azure Synapse Analytics: Será utilizado para el análisis de datos. Synapse Analytics ofrece capacidades de procesamiento de datos en batch y en tiempo real, así como integración con Power BI para la visualización.

3. Estructura de Carpetas y Estrategia de Particionado

La estructura de carpetas en ADLS Gen2 se organizará de la siguiente manera:

  • /bronze/: Almacenará los datos raw de cada fuente.
  • /bronze/ventas/: Datos de ventas.
  • /bronze/inventarios/: Datos de inventarios.
  • /bronze/logistica/: Datos de logística y distribución.
  • /silver/: Almacenará los datos transformados y preparados para el análisis.
  • /silver/ventas/: Datos de ventas transformados.
  • /silver/inventarios/: Datos de inventarios transformados.
  • /silver/logistica/: Datos de logística y distribución transformados.

La estrategia de particionado se basará en la fecha de ingesta y en la naturaleza de los datos. Por ejemplo, los datos de ventas podrían particionarse por fecha de venta y tipo de producto.

4. Políticas de Retención y Tier de Acceso

  • Políticas de Retención: Se establecerán políticas de retención basadas en la relevancia de los datos para el negocio y los requisitos legales. Por ejemplo, los datos de ventas y inventarios podrían retenerse durante 5 años, mientras que los datos de logística podrían retenerse durante 2 años.
  • Tier de Acceso: Se utilizarán diferentes tiers de acceso en ADLS Gen2 para gestionar el costo y el acceso a los datos. Los datos más recientes y frecuentemente accedidos se almacenarán en un tier de acceso rápido, mientras que los datos menos recientes se moverán a un tier de acceso más lento y económico.

5. Consideraciones de Seguridad y Gobierno de Acceso

  • Autenticación y Autorización: Se implementarán medidas de autenticación y autorización utilizando Azure Active Directory (AAD) para controlar quién puede acceder y modificar los datos.
  • Cifrado: Todos los datos en tránsito y en reposo estarán cifrados utilizando tecnologías como SSL/TLS y Azure Storage Service Encryption.
  • Gobierno de Datos: Se establecerán políticas de gobierno de datos claras, definiendo roles y responsabilidades para la gestión de la calidad, seguridad y privacidad de los datos.

6. Riesgos y Recomendaciones Operativas

  • Monitoreo Continuo: Es crucial monitorear continuamente la arquitectura para identificar posibles problemas de rendimiento, seguridad o calidad de datos.
  • Capacitación del Personal: Se recomienda capacitar al personal en las mejores prácticas de manejo de datos, seguridad y uso de los servicios de Azure.
  • Escalabilidad: La arquitectura debe ser escalable para adaptarse al crecimiento futuro de los datos y las necesidades del negocio.

Esta propuesta de arquitectura de almacenamiento está diseñada para satisfacer las necesidades de FarmaNorte, ofreciendo una solución escalable, segura y eficiente para la gestión de sus datos.

04 Procesamiento ETL

Transformación, calidad de datos y orquestación
Databricks · Synapse

Capa de Procesamiento y ETL para FarmaNorte

Basándonos en el análisis previo de fuentes, ingesta y almacenamiento, y considerando el perfil del cliente, volumen de datos y complejidad de las transformaciones, se decidirá entre Databricks y Azure Synapse Analytics para diseñar la capa de procesamiento.

1. Decisión y justificación entre Databricks y Synapse

Después de evaluar las necesidades específicas de FarmaNorte, se concluye que Azure Synapse Analytics es suficiente para manejar el volumen de datos y la complejidad de las transformaciones requeridas. Synapse ofrece una plataforma escalable y eficiente para el procesamiento de datos, y su integración con otros servicios de Azure, como Azure Data Factory y Power BI, facilita la orquestación y la visualización de los datos. Además, el equipo de FarmaNorte puede operar Synapse sin necesidad de ingenieros de datos senior, lo que reduce la complejidad operativa y los costos.

No se justifica el uso de Databricks en este caso, ya que el volumen de datos y la complejidad de las transformaciones no requieren la potencia adicional que ofrece Spark en Databricks. Además, el equipo de FarmaNorte no tiene la necesidad de procesar grandes conjuntos de datos en un entorno de Big Data, lo que reduce la necesidad de una solución como Databricks.

2. Transformaciones principales por capa

La capa de procesamiento se dividirá en tres capas: Bronze, Silver y Gold.

  • Capa Bronze: En esta capa, se realizarán las transformaciones básicas de datos, como la limpieza y el formato de los datos. Se utilizarán Azure Data Factory y Azure Synapse Analytics para realizar estas transformaciones.
  • Capa Silver: En esta capa, se realizarán transformaciones más complejas, como la agregación y el análisis de los datos. Se utilizarán Azure Synapse Analytics y Azure Machine Learning para realizar estas transformaciones.
  • Capa Gold: En esta capa, se almacenarán los datos transformados y listos para su análisis y visualización. Se utilizará Azure Synapse Analytics y Power BI para realizar la visualización y el análisis de los datos.

Las transformaciones principales que deben ocurrir en esta capa incluyen:

  • La limpieza y el formato de los datos de ventas, stock y logística.
  • La agregación de los datos de ventas y stock por región y producto.
  • La creación de un modelo de previsión de demanda utilizando Azure Machine Learning.
  • La integración de los datos de logística y stock para reducir roturas de stock y capital inmovilizado en almacén.

3. Estrategia de calidad de datos y validaciones

La estrategia de calidad de datos y validaciones incluirá las siguientes etapas:

  • Validación de datos: Se validarán los datos de entrada para asegurarse de que sean correctos y completos.
  • Detección de anomalías: Se detectarán las anomalías en los datos y se alertará al equipo de FarmaNorte para su revisión y corrección.
  • Reconciliación de datos: Se reconciliarán los datos de diferentes fuentes para asegurarse de que sean consistentes y precisos.
  • Monitoreo de la calidad de los datos: Se monitoreará la calidad de los datos en tiempo real para detectar cualquier problema o anomalía.

4. Orquestación y scheduling de jobs

La orquestación y el scheduling de jobs se realizarán utilizando Azure Data Factory y Azure Synapse Analytics. Los jobs se programarán para ejecutarse automáticamente en intervalos regulares, como diariamente o semanalmente, dependiendo de las necesidades de FarmaNorte.

5. Riesgos operativos y recomendaciones de mantenimiento

Los riesgos operativos incluyen:

  • Fallas en la ingesta de datos: Se pueden producir fallos en la ingesta de datos debido a problemas con las fuentes de datos o con la infraestructura de Azure.
  • Problemas de rendimiento: Se pueden producir problemas de rendimiento debido a la gran cantidad de datos o a la complejidad de las transformaciones.
  • Fallas en la seguridad: Se pueden producir fallos en la seguridad debido a la falta de cumplimiento con las políticas de seguridad de Azure.

Para mitigar estos riesgos, se recomienda:

  • Monitorear la ingesta de datos y la infraestructura de Azure: Se debe monitorear la ingesta de datos y la infraestructura de Azure para detectar cualquier problema o anomalía.
  • Realizar pruebas y validaciones: Se deben realizar pruebas y validaciones regulares para asegurarse de que los jobs se ejecutan correctamente y que los datos son precisos.
  • Cumplir con las políticas de seguridad de Azure: Se debe cumplir con las políticas de seguridad de Azure para asegurarse de que los datos estén seguros y protegidos.

En resumen, la capa de procesamiento y ETL para FarmaNorte se diseñará utilizando Azure Synapse Analytics y Azure Data Factory. Se realizarán transformaciones básicas y complejas en las capas Bronze, Silver y Gold, y se utilizará Azure Machine Learning para crear un modelo de previsión de demanda. La estrategia de calidad de datos y validaciones incluirá la validación de datos, la detección de anomalías, la reconciliación de datos y el monitoreo de la calidad de los datos. La orquestación y el scheduling de jobs se realizarán utilizando Azure Data Factory y Azure Synapse Analytics, y se mitigarán los riesgos operativos mediante la monitorización, las pruebas y validaciones, y el cumplimiento con las políticas de seguridad de Azure.

| Opción | Ventajas | Desventajas | Por qué la elegimos |

2️⃣ Entidades principales del modelo (hechos, dimensiones o equivalentes)

2.1 Tabla de Hechos

| Nombre | Descripción | Granularidad | Columnas clave (ejemplo) |
|--------|-------------|--------------|--------------------------|
| FactVentas | Cada línea de venta (pedido) confirmada. | Por línea de pedido (producto × fecha × tienda). | VentaID, FechaID, ProductoID, ClienteID, TiendaID, CanalID, Cantidad, PrecioUnitario, Descuento, Costo, Ingresos, MargenBruto. |
| FactInventario | Estado de stock al cierre de cada día por ubicación. | Por día × producto × ubicación. | InventarioID, FechaID, ProductoID, AlmacenID, CantidadDisponible, CantidadReservada, ValorInventario. |

> Nota: Cada tabla de hechos contiene columnas de tipo “degenerate” (p. ej. VentaID) para permitir trazabilidad a los sistemas origen sin crear dimensiones adicionales.

3️⃣ Métricas de negocio clave y cálculos precalculados

| Métrica | Fórmula (DAX/SQL) | Tipo | Comentario de precálculo |
|---------|-------------------|------|--------------------------|
| Ingresos Totales | SUM(FactVentas.Ingresos) | Medida | Se almacena en la tabla de hechos (Ingresos = Cantidad PrecioUnitario (1‑Descuento)). |
| Margen Bruto | SUM(FactVentas.MargenBruto) | Medida | MargenBruto = Ingresos – Costo. |
| Rotura de Stock (Days Out of Stock) | COUNTROWS(FILTER(FactInventario, CantidadDisponible = 0)) por producto/fecha | Medida | Se calcula sobre la tabla de inventario; se crea una tabla agregada FactRotura con el número de días sin stock por mes para acelerar los dashboards ejecutivos. |
| Inventario Inmovilizado (€) | SUM(FactInventario.ValorInventario) | Medida | Precálculo diario en FactInventario. |
| Cobertura de Demanda | DIVIDE(SUM(FactVentas.Cantidad), SUM(FactPronostico.DemandaPrevista), 0) | Medida | Permite comparar ventas reales vs. pronóstico. |
| Error Absoluto del Pronóstico (MAE) | AVG(ABS(FactVentas.Cantidad - FactPronostico.DemandaPrevista)) | Medida | Se materializa en tabla FactPronosticoError a nivel semanal. |
| Tasa de Cumplimiento de Pedidos | DIVIDE(SUM(CASE WHEN FactVentas.CantidadEntregada >= FactVentas.Cantidad THEN 1 ELSE 0 END), COUNT(FactVentas.VentaID)) | Medida | Se guarda en tabla de hechos FactCumplimiento. |
| Ciclo de Reposición (días) | DATEDIFF(MIN(FactLogistica.FechaEntrada), MAX(FactLogistica.FechaSalida), DAY) por producto/almacén | Medida | Se precalcula en tabla FactCicloReposicion (una fila por mes). |
| Valor de Stock por Región | SUMX(RELATEDTABLE(FactInventario), FactInventario.ValorInventario) | Medida | Disponible en el modelo a nivel de dimensión DimRegion. |
| KPIs de Ventas por Canal | SUM(FactVentas.Ingresos), SUM(FactVentas.Cantidad) filtrados por DimCanal | Medida | Se exponen como perspectives en AS. |

Estrategia de pre‑agregación

  • Tablas de agregados (FactVentasMes, FactInventarioMes, FactRotura_Mes) se generan nightly con CTAS en Synapse.
  • Estas tablas alimentan directamente los visuales de nivel de alta granularidad (dashboards ejecutivos) y reducen el tiempo de respuesta a < 2 s.
  • En la capa AS, se definen measure groups que apuntan a la tabla de detalle y a las tablas de agregados, con la opción “Aggregation Awareness”.

4️⃣ Estrategia de actualización y latencia de datos

| Tipo de datos | Frecuencia | Origen | Proceso de carga | Ventana de disponibilidad |
|----------------|------------|--------|------------------|----------------------------|
| Ventas diarias | Near‑real‑time (5‑15 min) | Sistema ERP / POS (API) | ADF → Synapse Streaming / COPY → tabla StgVentas → MERGE incremental a FactVentas (SCD 0). | < 30 min después del cierre del ticket. |
| Inventario (stock) | Diario (cierre del día) | Sistema WMS | ADF batch nightly → StgInventario → MERGE a FactInventario (SCD 1). | Disponible a las 08:00 h del día siguiente. |
| Logística (movimientos) | Diario | Sistema TMS | ADF → StgLogistica → INSERT a FactLogistica. | Disponible a las 09:00 h. |
| Pronóstico de demanda | Semanal (lunes 02:00 h) | Azure ML pipeline | Modelo escribe resultados en StgPronostico → REPLACE en FactPronostico. | Visible en Power BI a las 04:00 h. |
| Dimensiones (cambios de atributos) | Cada 6 h | Sistemas maestros | CDC (Change Data Capture) → StgDim → SCD 2 MERGE en dimensiones. | Latencia ≤ 6 h. |
| Tablas de agregados | Nightly (02:30 h) | Fact tables | CTAS + INSERT OVERWRITE en Synapse. | Refrescadas antes de la jornada laboral. |

  • Persistencia: Todas las tablas están en Synapse Dedicated SQL Pool con distribución hash en las columnas de mayor cardinalidad (ProductoID, FechaID) y distribución round‑robin en tablas de dimensiones.
  • Control de calidad: Cada carga ejecuta procedimientos almacenados de validación (checksums, recuentos) y escribe resultados en tabla de auditoría FactCargaLog. Si falla, se envía alerta a Teams/Power Automate.
  • Reprocesamiento: En caso de corrección de datos fuente, se permite re‑ejecución puntual de los pipelines ADF con parámetros de rango de fechas, sin impactar el resto de la carga.

| Consumidor | Punto de acceso | Tecnologías | Detalles de implementación |

06 Machine Learning & MLOps

Estrategia de Machine Learning y MLOps para FarmaNorte

1. Casos de uso de ML priorizados y tipo de modelo recomendado por caso

1.1 Pronóstico de demanda diaria por producto y zona

  • Tipo de modelo: Prophet (o ARIMA con ajuste de calendarios y festividades).
  • Justificación: Los volúmenes de ventas son moderados y la serie temporal es estable. Prophet permite incluir calendarios de fin de semana y días festivos, se adapta bien a datos con estacionalidad diaria y es de bajo coste computacional, lo que facilita el reentrenamiento frecuente sin sobrecargar la infraestructura.
  • Objetivo de negocio: Reducir roturas de stock en un 15 % y optimizar la rotación de inventario, logrando una cobertura de demanda ≥ 95 % en los puntos de venta.

1.2 Identificación de patrones de ruptura de stock (anomalías)

  • Tipo de modelo: Auto‑encoder de series temporales (modelo de aprendizaje profundo ligero, por ejemplo, LSTM auto‑encoder) o algoritmo de detección de anomalías basado en aislamiento de bosque (Isolation Forest) aplicado a métricas de stock.
  • Justificación: Se necesita un modelo que pueda trabajar con datos de inventario diarios y detectar desviaciones anómalas sin requerir grandes volúmenes de datos de entrenamiento. Isolation Forest es simple, rápido y no necesita ajustes de hiperparámetros complicados.
  • Objetivo de negocio: Alertar a los equipos de logística al menos 24 h antes de una ruptura, reduciendo los costos asociados a la pérdida de ventas y a la gestión de pedidos urgentes.

1.3 Optimización de la cadena de suministro (reorden automático)

  • Tipo de modelo: Regresión lineal con variables de control (promociones, fecha de vencimiento, capacidad de almacén) o modelo de aprendizaje por refuerzo simple (policy gradient) para decidir órdenes de reabastecimiento.
  • Justificación: El objetivo es obtener una regla de reorden que minimice el costo de inventario y el de faltas. Una regresión lineal es interpretable y fácil de mantener, mientras que la RL puede mejorar la toma de decisiones en escenarios dinámicos, pero requiere mayor madurez de datos (promociones, precios dinámicos).
  • Objetivo de negocio: Reducir el capital inmovilizado en inventario en un 10 % manteniendo la cobertura de demanda.

1. Arquitectura de Power BI: modo de conexión y justificación

La arquitectura de Power BI se diseñará para conectar con la capa de datos subyacente en Azure Synapse Analytics. Debido al volumen de datos y la frecuencia de actualización, se recomienda utilizar el modo DirectQuery. Esto permitirá a los usuarios interactuar con los datos en tiempo real y obtener información actualizada sin necesidad de cargar los datos en Power BI.

La justificación para esta decisión es que el volumen de datos es moderado y la frecuencia de actualización es diaria, lo que no requiere un gran esfuerzo de procesamiento para actualizar los datos en Power BI. Además, el uso de DirectQuery permite una mayor flexibilidad y escalabilidad en la conexión con la capa de datos subyacente.

2. Estructura de workspaces y modelo de gobernanza

La estructura de workspaces de Power BI se diseñará para reflejar la organización y los roles de los usuarios dentro de FarmaNorte. Se crearán workspaces separados para cada departamento o equipo, como:

  • Dirección: Workspace para la dirección y los equipos de liderazgo.
  • Operaciones: Workspace para los equipos de operaciones y logística.
  • Análisis: Workspace para los equipos de análisis y reporting.

Cada workspace tendrá un propietario y un conjunto de miembros con permisos definidos para garantizar la seguridad y el control de acceso a los datos.

El modelo de gobernanza se basará en roles y responsabilidades claras, con un propietario de datos y un equipo de stewards de datos que serán responsables de la calidad, la seguridad y el cumplimiento normativo de los datos.

Arquitectura Propuesta para FarmaNorte

La arquitectura propuesta para FarmaNorte tiene como objetivo cumplir con los requisitos del proyecto, que incluyen la unificación de información de ventas, stock y logística, y la incorporación de un modelo de previsión de demanda. A continuación, se describe la arquitectura propuesta:

Capa de Ingesta y Almacenamiento

La capa de ingesta y almacenamiento se compone de varios componentes que permiten la ingesta de datos de diferentes orígenes y su almacenamiento en un formato adecuado para su procesamiento y análisis.

  • Origen de Datos: Los orígenes de datos identificados son el ERP (SAP Business One), el sistema de almacén (SQL Server) y el CRM de ventas (Salesforce).
  • Ingesta de Datos: Se utilizará Azure Data Factory (ADF) para ingerir datos de los orígenes mencionados. ADF es una herramienta de ingesta de datos que permite la ingesta de datos de diferentes orígenes y su almacenamiento en Azure.
  • Almacenamiento de Datos: Los datos ingeridos se almacenarán en Azure Data Lake Storage (ADLS) Gen2. ADLS Gen2 es un almacenamiento de datos escalable y seguro que permite el almacenamiento de grandes cantidades de datos en formato bruto.

Capa de Procesamiento y Análisis

La capa de procesamiento y análisis se compone de varios componentes que permiten el procesamiento y análisis de los datos almacenados.

  • Plataforma de Datos: Se utilizará Azure Synapse Analytics como plataforma de datos centralizada. Azure Synapse Analytics es una plataforma de datos que ofrece capacidades de almacenamiento y procesamiento de grandes cantidades de datos.
  • Transformación de Datos: Los datos almacenados en ADLS Gen2 se transformarán y procesarán utilizando Azure Synapse Analytics. Esto permitirá la creación de un conjunto de datos procesados y listos para ser utilizados por el modelo de previsión de demanda.

Capa de Inteligencia Artificial y Machine Learning

La capa de inteligencia artificial y machine learning se compone de varios componentes que permiten el desarrollo y despliegue del modelo de previsión de demanda.

  • Desarrollo de Modelos: Se utilizará Azure Machine Learning (AML) para desarrollar el modelo de previsión de demanda. AML es una plataforma de machine learning que permite el desarrollo y despliegue de modelos de machine learning.
  • Entrenamiento y Despliegue: El modelo de previsión de demanda se entrenará y desplegará utilizando AML. Esto permitirá la integración del modelo con la plataforma de datos y la generación de predicciones de demanda.

Capa de Visualización

La capa de visualización se compone de varios componentes que permiten la visualización de los resultados del modelo de previsión de demanda.

  • Herramienta de Visualización: Se utilizará Power BI como herramienta de visualización. Power BI es una herramienta de visualización que permite la creación de dashboards y informes interactivos.

Consideraciones de Seguridad y Cumplimiento

La seguridad y el cumplimiento normativo son fundamentales en la arquitectura propuesta.

  • Autenticación y Autorización: Se implementarán mecanismos de autenticación y autorización adecuados en todas las capas de la arquitectura. Esto garantizará que solo los usuarios autorizados puedan acceder a los datos y a los componentes de la arquitectura.
  • Cifrado de Datos: Los datos se cifrarán en tránsito y en reposo. Esto garantizará la confidencialidad y la integridad de los datos.
  • Cumplimiento Normativo: La arquitectura propuesta cumple con las normativas relevantes, como GDPR, normativa sanitaria y trazabilidad del medicamento.

Justificación y Supuestos

La arquitectura propuesta se ha diseñado teniendo en cuenta los requisitos del proyecto y las necesidades del cliente.

  • Se asume que el cliente tiene una conectividad estable y segura a Azure.
  • Se supone que los orígenes de datos proporcionan datos de calidad y consistentes.
  • La arquitectura propuesta está diseñada para escalar horizontalmente según sea necesario.

En resumen, la arquitectura propuesta para FarmaNorte es una arquitectura escalable y segura que cumple con los requisitos del proyecto. La arquitectura se compone de varias capas, incluyendo la ingesta y almacenamiento de datos, el procesamiento y análisis de datos, la inteligencia artificial y machine learning, y la visualización. La seguridad y el cumplimiento normativo son fundamentales en la arquitectura propuesta.

Procesos de Gobernanza del Dato

  • Proceso de Procesamiento de Datos: El proceso de procesamiento de datos establece cómo se procesarán y transformarán los datos para su uso en la plataforma de datos.
  • Proceso de Desarrollo de Modelos de AI: El proceso de desarrollo de modelos de AI establece cómo se desarrollarán y desplegarán los modelos de AI en la plataforma de datos.

Mecanismos de Control

  • Auditorías de Calidad de Datos: Se realizarán auditorías periódicas para verificar la calidad de los datos y para identificar áreas de mejora.
  • Monitoreo de Seguridad: Se implementará un sistema de monitoreo de seguridad para detectar posibles amenazas y vulnerabilidades en la plataforma de datos.
  • Evaluación de Modelos de AI: Se evaluarán periódicamente los modelos de AI para asegurar que sean transparentes, explicables y éticos.

Justificación y Supuestos

La propuesta de gobernanza del dato y AI para FarmaNorte se ha diseñado teniendo en cuenta los requisitos del proyecto y las necesidades del cliente. Se asume que el cliente tiene una conectividad estable y segura a Azure y que los orígenes de datos proporcionan datos de calidad y consistentes. La gobernanza del dato y AI es fundamental para asegurar que la plataforma de datos y los modelos de AI sean precisos, completos y consistentes, y que cumplan con las normativas relevantes.

Análisis Crítico del Problema de Negocio y Madurez de Datos Actual

FarmaNorte, una empresa de distribución farmacéutica con aproximadamente 350 empleados, busca implementar una plataforma de datos con un componente predictivo para unificar información de ventas, stock y logística, e incorporar un modelo de previsión de demanda. El objetivo es reducir roturas de stock, disminuir el inventario inmovilizado y lograr una exactitud del modelo de previsión de demanda por encima del 85%. Actualmente, la empresa utiliza Excel para consolidar informes de ventas de forma manual semanal, sin un data warehouse ni plataforma de BI en producción.

La madurez de datos actual de FarmaNorte es baja, ya que no cuenta con un data warehouse ni plataforma de BI centralizada, lo que dificulta la toma de decisiones informadas. La empresa depende de procesos manuales y no tiene una visión integral de sus datos. Esto limita su capacidad para analizar tendencias, identificar oportunidades de mejora y optimizar sus operaciones.

Propuesta de Funcionalidades Clave de IA/Data

Para abordar el problema de negocio y mejorar la madurez de datos de FarmaNorte, se proponen las siguientes funcionalidades clave de IA/Data:

  1. Modelo Predictivo de Previsión de Demanda: Desarrollar un modelo de machine learning que prediga la demanda futura de productos farmacéuticos, teniendo en cuenta factores como la estacionalidad, tendencias de ventas y eventos externos.
  2. Integración de Datos de Ventas, Stock y Logística: Implementar una plataforma de datos que integre información de ventas, stock y logística, proporcionando una visión integral de las operaciones de FarmaNorte.
  3. Análisis de Roturas de Stock y Optimización de Inventario: Desarrollar un análisis que identifique las causas de roturas de stock y proporcione recomendaciones para optimizar el inventario y reducir pérdidas.

Roadmap Técnico

A continuación, se detalla el roadmap técnico para cada funcionalidad:

  1. Modelo Predictivo de Previsión de Demanda:
  • Fuentes de datos: Datos de ventas históricas, información de productos, estacionalidad y eventos externos.
  • Tipo de análisis: Machine learning (regresión, series temporales).
  • Integración en el flujo de trabajo: El modelo se integrará en la plataforma de datos y se utilizará para generar predicciones de demanda que se utilizarán para optimizar el inventario y reducir roturas de stock.
  1. Integración de Datos de Ventas, Stock y Logística:
  • Fuentes de datos: Datos de ventas, stock y logística de diferentes orígenes (ERP, sistema de almacén, CRM de ventas).
  • Tipo de análisis: Integración de datos, ETL (Extract, Transform, Load).
  • Integración en el flujo de trabajo: La plataforma de datos se utilizará para integrar los datos de diferentes orígenes y proporcionar una visión integral de las operaciones de FarmaNorte.
  1. Análisis de Roturas de Stock y Optimización de Inventario:
  • Fuentes de datos: Datos de ventas, stock y logística.
  • Tipo de análisis: Análisis de datos, optimización de inventario.
  • Integración en el flujo de trabajo: El análisis se integrará en la plataforma de datos y se utilizará para identificar oportunidades de mejora y optimizar el inventario.

Valor de Negocio

La implementación de estas funcionalidades de IA/Data tendrá un impacto significativo en las métricas de éxito de FarmaNorte:

  • Reducción de roturas de stock: El modelo predictivo de previsión de demanda y el análisis de roturas de stock y optimización de inventario ayudarán a reducir las roturas de stock en al menos un 30%.
  • Disminución del inventario inmovilizado: La optimización de inventario y la reducción de roturas de stock ayudarán a disminuir el inventario inmovilizado y liberar capital.
  • Exactitud del modelo de previsión de demanda: El modelo predictivo de previsión de demanda tendrá una exactitud por encima del 85%, lo que permitirá a FarmaNorte tomar decisiones informadas y optimizar sus operaciones.

En resumen, la propuesta de funcionalidades clave de IA/Data y el roadmap técnico asociado ayudarán a FarmaNorte a mejorar su madurez de datos, reducir roturas de stock, disminuir el inventario inmovilizado y lograr una exactitud del modelo de previsión de demanda por encima del 85%.

Estrategia de Visualización de Datos para FarmaNorte

Introducción

La estrategia de visualización de datos para FarmaNorte tiene como objetivo proporcionar una visión integral de las operaciones de la empresa, permitiendo a los usuarios tomar decisiones informadas y optimizar sus procesos. La visualización de datos es fundamental para comunicar los insights y tendencias identificados en los datos, y para apoyar la toma de decisiones estratégicas.

Definición de KPIs de Visualización

A continuación, se definen los KPIs de visualización que se utilizarán para medir el éxito de la plataforma de datos:

  • Roturas de Stock: Número de roturas de stock por mes.
  • Inventario Inmovilizado: Valor del inventario inmovilizado por mes.
  • Exactitud del Modelo de Previsión de Demanda: Exactitud del modelo de previsión de demanda por mes.
  • Ventas: Ventas totales por mes.
  • Stock Disponible: Stock disponible por mes.

Diseño de Dashboards

Se proponen dos dashboards para FarmaNorte:

  • Dashboard Ejecutivo: Este dashboard proporcionará una visión general de las operaciones de la empresa, incluyendo los KPIs de visualización definidos anteriormente. El dashboard estará diseñado para ser utilizado por los directivos y gerentes de la empresa.
  • Dashboard de Operaciones Detallado: Este dashboard proporcionará una visión detallada de las operaciones de la empresa, incluyendo información sobre las roturas de stock, inventario inmovilizado y ventas. El dashboard estará diseñado para ser utilizado por los empleados de la empresa que se encargan de la gestión de inventario y ventas.

User Experience (UX)

La experiencia del usuario es fundamental para la adopción y uso efectivo de la plataforma de datos. A continuación, se describen las características de UX que se implementarán:

  • Filtros: Los usuarios podrán filtrar los datos por fecha, producto, ubicación y otros criterios relevantes.
  • Drill-downs: Los usuarios podrán profundizar en los datos para obtener información más detallada.
  • Alertas: Los usuarios podrán recibir alertas cuando se produzcan cambios significativos en los KPIs de visualización.

Stack de BI

Se recomienda utilizar Power BI como herramienta de visualización, debido a su capacidad para conectarse a diversas fuentes de datos, su facilidad de uso y su capacidad para crear dashboards y informes interactivos.

Data Consumers

Los data consumers de la plataforma de datos serán:

  • Directivos y Gerentes: Utilizarán la plataforma de datos para tomar decisiones estratégicas y obtener una visión general de las operaciones de la empresa.
  • Empleados de Gestión de Inventario y Ventas: Utilizarán la plataforma de datos para gestionar el inventario y las ventas, y para obtener información detallada sobre las operaciones de la empresa.

Implementación

La implementación de la estrategia de visualización de datos se realizará en las siguientes fases:

  • Fase 1: Diseño y desarrollo de los dashboards y la plataforma de datos.
  • Fase 2: Pruebas y validación de la plataforma de datos.
  • Fase 3: Implementación y capacitación de los usuarios.

Conclusión

La estrategia de visualización de datos para FarmaNorte tiene como objetivo proporcionar una visión integral de las operaciones de la empresa, permitiendo a los usuarios tomar decisiones informadas y optimizar sus procesos. La implementación de la plataforma de datos y los dashboards permitirá a la empresa mejorar su madurez de datos y alcanzar sus objetivos de negocio.

  2. Desarrollo de Conectores o APIs: Identificar y desarrollar los conectores o APIs necesarios para garantizar la integración de todos los sistemas con Azure Data Factory, asegurando la compatibilidad y la eficiencia en la ingesta de datos.

02 Ingesta de Datos

Estrategia y pipelines con Azure Data Factory
Azure Data Factory

Estrategia de Ingesta de Datos para FarmaNorte con Azure Data Factory

1. Patrón de Ingesta por Fuente o Grupo de Fuentes

Basándonos en el análisis de fuentes de datos realizado, se recomienda el siguiente patrón de ingesta para cada fuente o grupo de fuentes:

  • Sistema de Gestión Empresarial (ERP) - SAP Business One: Ingesta por batch diario, dado que los datos están estructurados y se actualizan con frecuencia. La ingesta debería enfocarse en capturar transacciones comerciales, producción, inventario y datos de empleados relevantes para el análisis.
  • Sistema de Almacén - SQL Server: Ingesta en tiempo real o batch diario, dependiendo de la frecuencia de actualización de los datos. La ingesta debería centrarse en inventarios, movimientos de stock y ubicaciones de almacén para garantizar una visión precisa de la logística.
  • CRM de Ventas - Salesforce: Ingesta en tiempo real, ya que los datos de interacciones con clientes, historial de ventas, oportunidades y leads son cruciales para el análisis de ventas y la previsión de demanda. Es importante asegurar la calidad de los datos y la compatibilidad con Azure Data Factory.
  • Datos de Producción: Ingesta batch diario o semanal, dependiendo de la frecuencia de producción y la disponibilidad de los datos. La ingesta debería enfocarse en información sobre lotes, fechas de producción, cantidad producida, etc.
  • Datos de Logística y Distribución: Ingesta en tiempo real o batch diario, centrada en información sobre transporte, entrega y distribución de productos. La calidad y consistencia de los datos son clave para el análisis de logística y la optimización de la cadena de suministro.

2. Estructura de Pipelines Recomendada en ADF

Para cada fuente de datos, se debe diseñar un pipeline específico en Azure Data Factory (ADF) que refleje el patrón de ingesta recomendado. La estructura de los pipelines debe incluir:

  • Origen de Datos: Conector específico para cada fuente de datos (SAP Business One, SQL Server, Salesforce, etc.).
  • Actividad de Copia: Configuración para copiar los datos desde el origen hasta el destino (Azure Data Lake Storage Gen2).
  • Transformación de Datos: Actividades de transformación para limpiar, formatear y enriquecer los datos según sea necesario antes de llegar al almacenamiento.
  • Destino de Datos: Configuración para almacenar los datos transformados en Azure Data Lake Storage Gen2.

3. Conectores y Configuraciones Clave

  • Conector SAP Business One: Utilizar el conector ADF para SAP para conectarse al ERP y copiar los datos relevantes. Es crucial configurar las consultas y los parámetros para capturar todos los datos necesarios.
  • Conector SQL Server: Utilizar el conector ADF para SQL Server para conectarse al sistema de almacén y copiar los datos de inventario y logística.
  • Conector Salesforce: Utilizar el conector ADF para Salesforce para conectarse al CRM y copiar los datos de ventas y clientes. Debe configurarse para manejar la autenticación y la autorización adecuadamente.
  • Conectores para Datos de Producción y Logística: Dependiendo del formato y la ubicación de estos datos, pueden utilizarse conectores genéricos como el conector de archivo (para CSV, JSON, etc.) o desarrollar conectores personalizados si es necesario.

4. Cadencias y Dependencias entre Pipelines

  • Cadencia de Ejecución: Los pipelines deben programarse para ejecutarse con la frecuencia adecuada según el patrón de ingesta definido para cada fuente. Por ejemplo, los pipelines para el ERP y el sistema de almacén podrían ejecutarse diariamente, mientras que el pipeline para el CRM de ventas podría ejecutarse en tiempo real o con una frecuencia más alta.
  • Dependencias: Debe definirse una dependencia entre pipelines si la ejecución de uno depende del éxito de otro. Por ejemplo, un pipeline de transformación podría depender de que los datos hayan sido copiados con éxito desde el origen.

5. Riesgos Identificados y Recomendaciones de Mitigación

  • Riesgo de Calidad de Datos: La calidad de los datos en las fuentes puede variar, lo que podría afectar la precisión del análisis. Recomendación: Realizar una evaluación detallada de la calidad de los datos y aplicar transformaciones y validaciones necesarias en los pipelines de ADF.
  • Riesgo de Integración: La integración de sistemas y la compatibilidad de los conectores pueden ser desafíos. Recomendación: Desarrollar o adquirir conectores personalizados si es necesario y realizar pruebas exhaustivas para asegurar la integración exitosa.
  • Riesgo de Seguridad y Permiso: El acceso a los datos y la seguridad son cruciales. Recomendación: Trabajar con los departamentos de IT y seguridad para asegurar que todos los permisos y protocolos de seguridad estén en lugar antes de comenzar la ingesta de datos.

Al considerar estos factores y diseñar una estrategia de ingesta de datos sólida con Azure Data Factory, FarmaNorte puede asegurar una base de datos robusta y confiable para su análisis y toma de decisiones, mitigando los riesgos asociados con la calidad, la integración y la seguridad de los datos.

03 Almacenamiento

Arquitectura de Data Lake con capas medallion
ADLS Gen2 · Synapse

Propuesta de Arquitectura de Almacenamiento para FarmaNorte

1. Decisión y Justificación sobre la Estructura de Capas

Basándonos en el análisis de fuentes de datos y la estrategia de ingesta definida, recomendamos una arquitectura de almacenamiento que sigue un enfoque simplificado de dos capas, en lugar de la arquitectura medallion completa (Bronze, Silver, Gold). Esta decisión se justifica por varios motivos:

  • Volumen y Complejidad de Datos: El volumen de datos estimado y la complejidad de las fuentes sugieren que una arquitectura de dos capas (similar a Bronze y Gold) podría ser suficiente para satisfacer las necesidades de FarmaNorte, sin la necesidad de una capa intermedia (Silver) que añadiría complejidad adicional.
  • Nivel de Madurez del Cliente: Considerando el nivel de madurez actual de FarmaNorte en términos de gestión de datos y análisis, una arquitectura más simple facilitará la adopción y operación continua.
  • Requisitos del Proyecto: Los objetivos del proyecto se centran en la integración de datos de ventas, stock y logística, y el desarrollo de un modelo predictivo de previsión de demanda. Una arquitectura de dos capas apoyará estos objetivos de manera efectiva.

2. Servicios de Azure Recomendados y Justificación

  • Azure Data Lake Storage (ADLS) Gen2: Para el almacenamiento de datos. ADLS Gen2 ofrece un almacenamiento escalable y seguro para todo tipo de datos, y se integra bien con otros servicios de Azure como Azure Data Factory (ADF) y Azure Synapse Analytics.
  • Azure Data Factory (ADF): Para la ingesta y transformación de datos. ADF permite la creación de pipelines para mover y transformar datos desde diversas fuentes hasta ADLS Gen2.
  • Azure Synapse Analytics: Para el análisis y procesamiento de datos. Synapse Analytics proporciona capacidades de análisis avanzado y machine learning, integrándose con ADLS Gen2 para procesar y analizar los datos almacenados.

3. Estructura de Carpetas y Estrategia de Particionado

  • Estructura de Carpetas: Se propone una estructura de carpetas en ADLS Gen2 que refleje las diferentes áreas de datos:
  • /raw: Para datos crudos e ingestados directamente desde las fuentes.
  • /processed: Para datos procesados y transformados, listos para análisis.
  • Estrategia de Particionado: Se recomienda particionar los datos basado en la fecha de ingesta o la fecha de evento, lo que facilitará la gestión y el análisis de grandes conjuntos de datos.

4. Políticas de Retención y Tier de Acceso

  • Políticas de Retención: Establecer políticas de retención basadas en los requisitos legales y de negocio de FarmaNorte. Por ejemplo, datos de transacciones podrían retenerse por un período determinado según regulaciones específicas.
  • Tier de Acceso: Implementar una estrategia de tier de acceso para optimizar el costo. Los datos más recientemente utilizados o de acceso frecuente se almacenarán en un tier de acceso rápido, mientras que los datos menos frecuentemente accedidos se moverán a tiers más económicos.

5. Consideraciones de Seguridad y Gobierno de Acceso

  • Autenticación y Autorización: Utilizar Azure Active Directory (AAD) para la autenticación y autorización de usuarios y servicios, asegurando que solo los usuarios autorizados puedan acceder a los datos.
  • Cifrado de Datos: Implementar el cifrado de datos tanto en tránsito como en reposo, utilizando tecnologías como Azure Storage Service Encryption.
  • Gobierno de Datos: Establecer políticas de gobierno de datos claras, definiendo roles y responsabilidades para la gestión de datos, calidad de datos y seguridad.

6. Riesgos y Recomendaciones Operativas

  • Monitoreo y Alertas: Configurar monitoreo y alertas en ADF y Synapse Analytics para detectar problemas de ingesta o análisis de datos.
  • Capacitación y Soporte: Proporcionar capacitación al equipo de FarmaNorte sobre la operación y mantenimiento de la arquitectura de datos propuesta.
  • Revisión y Ajuste: Regularmente revisar la arquitectura y las políticas de gestión de datos para asegurarse de que siguen alineadas con las necesidades cambiantes de FarmaNorte.

Esta propuesta de arquitectura de almacenamiento está diseñada para ser escalable, segura y alineada con los objetivos de FarmaNorte, proporcionando una base sólida para el análisis de datos y la toma de decisiones informadas.

Decisión y justificación entre Databricks y Synapse

Basándonos en la arquitectura de almacenamiento y la estrategia de ingesta definidas en el análisis previo, y considerando el perfil del cliente y el volumen de datos, decidimos que Azure Synapse Analytics es suficiente para cubrir las necesidades de procesamiento y transformación de datos de FarmaNorte. La justificación de esta decisión se basa en varios factores:

  1. Volumen de datos: Aunque no se proporciona un volumen específico, el análisis inicial sugiere que se trata de un conjunto de datos manejable para Synapse, especialmente considerando que los orígenes de datos incluyen sistemas de gestión como SAP Business One, SQL Server y Salesforce, que normalmente generan cantidades significativas pero no masivas de datos.
  1. Complejidad de las transformaciones: Las transformaciones necesarias, como la integración de datos de ventas, stock y logística, y el desarrollo de un modelo predictivo de previsión de demanda, pueden ser manejadas efectivamente por Synapse. Synapse ofrece capacidades de procesamiento de datos y análisis avanzados, incluyendo la integración con Azure Machine Learning para tareas de machine learning, lo que cubre las necesidades identificadas.
  1. Capacidad del equipo: Considerando que el equipo de FarmaNorte no cuenta con ingenieros de datos senior, y basándonos en el objetivo de diseñar una solución que el equipo pueda operar en seis meses sin nuestra supervisión directa, Synapse ofrece una plataforma más integrada y fácil de usar, con herramientas visuales para el diseño de pipelines de datos y la creación de workflows, lo que facilita su adopción y operación.

Transformaciones principales por capa

Las transformaciones de datos se dividen en varias capas, cada una con sus objetivos específicos:

  • Capa Bronze (Raw): En esta capa, se ingieren los datos desde las fuentes originales (SAP Business One, SQL Server y Salesforce) utilizando Azure Data Factory. Los datos se almacenan en su forma bruta en el Data Lake (Azure Data Lake Storage Gen2) para su posterior procesamiento.
  • Capa Silver (Transformed): Aquí, se aplican las transformaciones necesarias a los datos brutos para prepararlos para el análisis. Esto incluye la limpieza de datos, el manejo de valores nulos, la normalización y la agregación de datos según sea necesario. Synapse Analytics se utiliza para ejecutar estos procesos de transformación.
  • Capa Gold (Refined): En esta capa, los datos transformados se refinan aún más para satisfacer las necesidades específicas de los modelos de análisis y los dashboards. Esto puede incluir la creación de vistas, la aplicación de lógica de negocio adicional y la preparación de datos para la visualización.

Estrategia de calidad de datos y validaciones

La estrategia de calidad de datos incluye:

  • Validaciones de ingreso: Se verifican los datos al ingresarse a la capa Bronze para asegurarse de quecumplen con los criterios básicos de formato y estructura.
  • Detección de anomalías: Se implementan reglas y algoritmos para detectar datos anómalos o inconsistentes en las capas Silver y Gold.
  • Reconciliación de datos: Se comparan los datos transformados con los datos originales para asegurarse de que las transformaciones se han realizado correctamente y no se han introducido errores.
  • Monitoreo continuo: Se establecen procesos para monitorear la calidad de los datos de manera continua, identificando y corrigiendo cualquier problema de manera proactiva.

Orquestación y scheduling de jobs

La orquestación y programación de los trabajos de procesamiento se realizarán mediante Azure Data Factory, que ofrece herramientas visuales para diseñar, programar y administrar pipelines de datos. Esto Permitirá:

  • Automatización: Automatizar los flujos de trabajo para que los datos se procesen y transformen de manera regular y consistente.
  • Programación: Programar los trabajos para que se ejecuten en momentos específicos del día o la semana, asegurando que los datos estén actualizados y listos para el análisis cuando sea necesario.
  • Monitoreo: Monitorear los trabajos para detectar cualquier error o problema, permitiendo una respuesta rápida y minimizando el tiempo de inactividad.

Riesgos operativos y recomendaciones de mantenimiento

Para mitigar los riesgos operativos y asegurar el mantenimiento adecuado de la capa de procesamiento y ETL, se recomiendan las siguientes acciones:

  • Capacitación del equipo: Proporcionar capacitación adecuada al equipo de FarmaNorte sobre el uso y el mantenimiento de la plataforma Synapse, así como sobre las mejores prácticas para la gestión de datos.
  • Monitoreo y respuesta: Establecer procesos de monitoreo continuo y tener un plan de respuesta para abordar cualquier problema que surja, minimizando el impacto en la operación.
  • Actualizaciones y parches: Mantener la plataforma y las herramientas actualizadas con los últimos parches de seguridad y actualizaciones de funcionalidad, asegurando la protección y la eficiencia del sistema.
  • Documentación: Mantener una documentación detallada y actualizada sobre la arquitectura, los procesos y las configuraciones, facilitando la resolución de problemas y el mantenimiento a largo plazo.

Al seguir esta propuesta, FarmaNorte podrá implementar una capa de procesamiento y ETL eficaz y sostenible, que satisfaga sus necesidades de análisis de datos y apoye su toma de decisiones empresariales.

3. Métricas de negocio clave y cálculos precalculados

| Métrica (KPIs) | Tabla de origen | Cálculo (pre‑agregado o medida DAX) | Comentario de negocio |
|----------------|----------------|------------------------------------|-----------------------|
| Roturas de Stock | FactStockShortage | SUM(ShortageQty) y AVG(DurationDays) | Se muestra por producto, tienda y período. |
| Inventario Inmovilizado | FactInventory | SUM(CASE WHEN DaysInStock > 180 THEN StockValue ELSE 0 END) | Días en stock calculado a partir de DimDate – LastMovementDate. |
| Exactitud del Forecast | FactDemandForecast vs FactSales (real) | MAE = AVG(ABS(ForecastQty - ActualQty)) ; MAPE = AVG(ABS(ForecastQty - ActualQty)/ActualQty) | Se calcula a nivel de producto‑tienda‑mes. |
| Cobertura de Demanda | FactSales vs FactInventory (stock disponible) | SUM(QtySold) / NULLIF(SUM(StockOnHand + InTransitQty),0) | Indicador de capacidad de atender la demanda. |
| Margen Bruto | FactSales | (GrossRevenue - CostOfGoodsSold) / GrossRevenue | Expone rentabilidad por producto y canal. |
| Lead Time Logístico | FactLogistics | AVG(LeadTimeDays) | Permite detectar cuellos de botella en la cadena. |
| Ventas por Canal | FactSales | SUM(NetRevenue) GROUP BY Channel | Dashboard ejecutivo. |
| Días de Inventario (Days of Inventory – DOI) | FactInventory | AVG(StockOnHand / (AVG(QtySold)/30)) | Medida de rotación de inventario. |
| Coste de Stock‑out | FactStockShortage (estimado) | SUM(LostRevenue) | Calculado con base en margen histórico. |
| Indicadores de Calidad de Datos | (Gold tables) | COUNT(*) WHERE ValidationFlag = 0 | Métrica de calidad para el Data Steward. |

Implementación:

  • En Synapse se crean tablas agregadas (materialized views) para los KPIs que requieren alta frecuencia (roturas de stock, inventario inmovilizado, lead time).
  • En Analysis Services (o Power BI) se definen medidas DAX que reutilizan esas tablas agregadas y añaden cálculos context‑aware (p.ej., “% de cobertura” con filtros de fecha y canal).
  • Las métricas críticas se precalculan diariamente (carga incremental) para evitar cálculos on‑the‑fly en los dashboards.

4. Estrategia de actualización y latencia de datos

| Nivel | Frecuencia | Tipo de carga | Detalles técnicos |
|-------|------------|---------------|-------------------|
| Bronze → Silver | Cada 15 min (near‑real‑time) | Copy incremental desde origen usando ADF + Change Data Capture (CDC) donde el origen lo soporte (SQL Server, SAP). | Los archivos parquet se versionan en ADLS Gen2. |
| Silver → Gold (DW) | Batch diario (ej. 02:00 h) y incremental cada hora para tablas críticas (FactSales, FactInventory). | Synapse Pipelines con MERGE y particiones por DimDate. | Se usan staging tables temporales y HASH de claves para detectar cambios. |
| Gold → Agregados (materialized views) | Refresh incremental cada 30 min (para KPI de roturas y stock) y refresh completo nocturno (para métricas históricas). | CREATE MATERIALIZED VIEW … WITH (REFRESH = ON DEMAND) y Azure Synapse Spark para cálculos pesados. |
| Gold → Analysis Services | Procesamiento completo cada 4 h (para datos operacionales) y process full al día (para histórico). | Azure Synapse Link + AS processing schedule (XMLA endpoint). |
| Modelos ML | Retraining semanal (lunes 04:00 h) usando datos de la última semana. | Azure Machine Learning pipelines que leen directamente de FactDemandForecast y FactSales. |

1. Casos de uso de ML priorizados y tipo de modelo recomendado por caso

  • Pronóstico de demanda de productos por tienda y por horizonte de 1‑3 meses
  • Tipo de modelo: 1️⃣ Prophet como punto de partida por su capacidad de modelar estacionalidad y eventos especiales sin requerir ingeniería de features compleja. 2️⃣ Una vez consolidados los datos, se introducirá XGBoost / LightGBM sobre features temporales, de inventario y de logística, que suele ofrecer una mejora de 10‑20 % en MAE respecto a Prophet cuando se dispone de suficiente volumen histórico.
  • Justificación: La curva de aprendizaje del equipo es mínima, los modelos se pueden entrenar en minutos, y ambos tienen implementaciones nativas en Azure ML (Python y R). Además, ambos son interpretables con SHAP o con los parámetros internos de importancia de variables.
  • Detección de roturas de stock en tiempo real
  • Tipo de modelo: Isolation Forest o One‑Class SVM sobre características de inventario (stock on‑hand, días en stock, velocidad de venta) y sobre métricas de demanda histórica.
  • Justificación: El objetivo es generar alertas cuando el stock cae por debajo de un umbral de seguridad; los modelos de detección de anomalías son rápidos de entrenar y fáciles de interpretar.
  • Optimización de inventario (re‑orden y nivel de stock de seguridad)
  • Tipo de modelo: Regresión de Gradient Boosting (XGBoost/LightGBM) que predice el punto de re‑orden y el nivel de stock de seguridad óptimo.
  • Justificación: Se necesita un modelo que combine demanda, lead time y variabilidad; el Boosted Tree logra capturar interacciones sin requerir una gran cantidad de datos estructurados.
  • Predicción de lead time logístico
  • Tipo de modelo: Regresión Random Forest o Linear Regression con polinomios que utiliza variables de origen, destino, transportista, condiciones climáticas y de tráfico (si están disponibles).
  • Justificación: Permite estimar de forma rápida el tiempo de entrega, fundamental para el cálculo del stock de seguridad.

1. Arquitectura de Power BI: modo de conexión y justificación

La arquitectura de Power BI se basará en una conexión a la capa semántica en Azure Analysis Services (o Power BI Premium Gen2), que a su vez se conecta al esquema en estrella en Synapse Analytics. El modo de conexión más adecuado para esta arquitectura es Import.

La justificación de esta decisión se basa en varios factores:

  • Volumen de datos: Aunque el volumen de datos es significativo, la capa semántica en Azure Analysis Services ya ha procesado y agregado los datos, lo que reduce la cantidad de datos que Power BI necesita manejar.
  • Frecuencia de actualización: La actualización de los datos se realiza de manera incremental y periódica, lo que permite a Power BI importar los datos actualizados de manera eficiente.
  • Complejidad de las consultas: Las consultas en Power BI se beneficiarán de la capa semántica en Azure Analysis Services, que proporciona un modelo tabular optimizado para consultas.
